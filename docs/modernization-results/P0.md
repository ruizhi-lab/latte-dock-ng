# P0: Repeatable performance baseline

Status: Pending validation.

## Scope

Establish repeatable A/A measurements and select representative scenarios
before choosing a performance implementation. No performance change was made
and no resource saving is claimed.

## Baseline build and invalid runtime attempt

The exact recorded source baseline, `e3ef1ddf001aa032cffa62db21cfd97196174746`,
configured and built successfully as Release in `/tmp/latte-p0-build` using
GCC 16.2.1, Qt 6.11.2 and KDE Frameworks 6.29.0. Its isolated installation
was copied to `/tmp/latte-p0-prefix` on the Fedora VM.

Before VM access, the host had no `latte-dock-ng` process and no `pidstat`
binary. A host `/usr/bin/latte-dock-ng --version` probe entered Qt/Wayland
startup and aborted because the sandbox denied `wl_display` creation; a 2.5 MiB
SIGABRT coredump was recorded. This probe was not a functional test or
measurement.

The temporary process was started with hand-built `QML_IMPORT_PATH`,
`QML2_IMPORT_PATH` and `XDG_DATA_DIRS` values. This did not follow the project's
user-install environment and did not establish a matching, isolated runtime
root. The user observed that task running-state dots/lines disappeared. The
temporary process was stopped and the Fedora system RPM was restarted from the
Plasma session environment. The user then confirmed the indicators were still
missing. No code was changed. The Fedora `lattedockrc` and layout were written
during the temporary run; no automatic backup or libvirt snapshot was found.
A private copy of the current post-incident files is under
`/tmp/latte-p0-after-state` in the VM. Do not treat the temporary profile as
valid performance evidence or modify this profile further until its original
state is recovered or the user directs a safe recovery.

The process did register `org.kde.lattedock`, but its startup log contained two

## Read-only indicator diagnosis

After the user confirmed that dots/lines were still absent, the Fedora session
was inspected without changing its profile or restarting the dock. The active
process was `/usr/bin/latte-dock-ng --replace`; its environment had no
`QML_IMPORT_PATH`, `QML2_IMPORT_PATH` or Qt plugin override, and
`XDG_DATA_DIRS` contained the normal Fedora session paths. `rpm -V latte-dock-ng`
reported no modified package files. The active layout still has
`[Containments][1][Indicator] enabled=true` and
`type=org.kde.latte.default`. The packaged Latte plasmoid keeps its local
indicator fallback enabled while the bridge is absent, and disables that
fallback only after the Latte bridge attaches.

At that point, these checks ruled out a persistent QML environment override,
modified RPM files, and an explicitly disabled default indicator. They did not
establish whether the running task model reports windows or whether the Latte
bridge and indicator component are producing their visual items. No root cause
is claimed.
Commands used were `rpm -V latte-dock-ng`, reading `/proc/5108/environ`, and
reading the active layout's indicator group and packaged plasmoid logic. This
restriction was superseded by the user's later explicit authorization to use
the VMs as GUI test sandboxes; the valid recovery and measurements below were
made after that authorization.

## Recovered GUI validation and valid idle A/A series

The user explicitly authorized Latte installation and configuration changes in
the Fedora and Debian VMs as GUI test sandboxes. Fedora was then installed from
the exact baseline with `bash install.sh --user Debug`; the dock ran from
`~/.local/bin/latte-dock-ng` with the installer-generated development
environment. The user confirmed that task status indicators returned. The user
also confirmed that the Fedora window preview works after relaunching from the
actual Plasma Wayland session environment. Preview-only, highlight-only and
preview-plus-highlight task-icon hover choices remain separate final checks.

The preview failure was reproduced in the first SSH-launched run: that process
had `XDG_SESSION_TYPE=tty` and no `DISPLAY` or `WAYLAND_DISPLAY`. Its preview
helper logged `could not connect to display`, could not load the `xcb` platform
plugin, and the documented repeated-failure fallback disabled previews. Plasma's
user service reported `DISPLAY=:0`, `WAYLAND_DISPLAY=wayland-0`,
`XDG_SESSION_TYPE=wayland`, `XDG_RUNTIME_DIR=/run/user/1000`,
`DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/1000/bus`, and the session's
`XAUTHORITY` path. Passing those values to the SSH launch restored helper
startup; the user confirmed the preview. The three SIGABRT helper coredumps
from the invalid launch remain in the Fedora coredump history. The fresh valid
launch produced no additional helper coredump during the preview check. The
user also confirmed that Debian's task status indicators are restored. After
the Debian 13 staging restart on the final branch, the user confirmed that the
configured `PreviewWindows` mode displays previews. Highlight-only and combined
modes remain untested.

After a Fedora user-mode Release install, five independent dock starts were
sampled with the same layout, display and user configuration. Each run used a
30-second warmup and a 60-second idle-visible window. The pointer remained at
the center of the display, outside the bottom dock. The layout SHA-256 was
unchanged (`c57ecbabc7843ade393a3106ec556e145e585bad4d20f392b4d37a77fd4e9346`).
Every window was marked valid by the process-family sampler. Raw records are in
[P0-idle-aa-2026-09-30.jsonl](P0-idle-aa-2026-09-30.jsonl).

All five runs are retained, including the higher-CPU first run. One continuous
instance also produced five valid consecutive windows; its PSS was about
265–267 MiB, higher than the independently restarted runs. That difference is
not evidence of a leak or a stable memory plateau. Context switches are a
proxy, not a wakeup count; RSS/PSS do not measure unique physical or GPU memory.
The Release startup log contained two Mesa EGL `failed to create dri2 screen`
warnings. They are recorded as VM graphics-environment warnings, not treated
as a clean-log pass. Fedora had no `powerprofilesctl` command, so the active
power profile could not be recorded.

A later canonical Debug trace used a synthetic QWidget probe that created five
windows 500 ms apart and kept them open through the ten-second measurement
window. The probe exited successfully and the generic tracker markers recorded
11 hint schedules and 14 executions; a separate ten-second quiet interval was
0/0. These counters are global work markers without window IDs, and this
single event trace is not an A/A performance pair or per-window cost estimate.
No titles, screenshots or user-window inventory were retained. Hidden-state and
edge-relocation measurements remain outstanding. The pointer-hover smoke is
inconclusive because the target task icon and active layout were not confirmed;
the current configuration finding below does not resolve those gaps. It does
not contradict the user's confirmation that Fedora previews work.

A read-only scan on 2026-09-30 found a persisted `hoverAction=PreviewWindows`
entry in one Fedora Latte layout file. This identifies a saved preview-only
choice, but does not establish that this layout was active during the earlier
pointer-hover smoke or that the pointer reached a task icon. The
`HighlightWindows` and `PreviewAndHighlightWindows` choices have not been
exercised in the desktop session. The sanitized command was
`grep -niE 'hoverAction|PreviewWindows|HighlightWindows|PreviewAndHighlightWindows' ~/.config/plasma-org.kde.plasma.desktop-appletsrc ~/.config/latte/*.layout.latte`;
it returned one `hoverAction=PreviewWindows` entry in a Latte layout file and
no matching Plasma applet-config entry. No layout contents were copied into

A temporary edge-relocation smoke changed only the active test layout's
containment location through top, left and right, restarting the user-mode
Debug dock each time. The fresh startup log reported the requested
`Plasma::Types::TopEdge`, `LeftEdge` and `RightEdge` respectively. The original
layout file was restored byte-for-byte from its private VM backup; the dock
restarted at its original bottom edge. This verifies edge selection and startup
geometry on one screen, not rapid superseding relocations, multiple screens or
hotplug.

An AutoHide-mode smoke temporarily changed the active view from AlwaysVisible
to AutoHide, moved the pointer between screen center and the bottom edge, and
confirmed the Debug dock stayed alive with no hint work during the transition.
The pointer's task target and actual hidden/shown visual state were not
observable through the approved marker-only path, so this is not accepted as a
hide/show behavior check. The exact layout backup was restored and the dock was
restarted in its original mode.

The read-only collector in `scripts/measure-process-family.py` samples only
the exact requested Latte executable paths and process start identities. It
records process CPU ticks, context switches and periodic `smaps_rollup` memory
values. It writes no configuration. The Fedora Release executable was built
from the recorded baseline with GCC 16.2.1 and Release optimization; the
compiler log contained no C++ warning/error lines.

## Initial profile evidence and candidate selection

`perf stat` was attached only to the active Latte PID for 20 seconds and
reported 6.427 task-clock seconds, 19,755 context switches, 183 CPU migrations
and 1,393 page faults. A separate 25-second process-scoped `perf record -g`
captured 36,870 CPU-cycle samples with zero lost samples. The profile attributes
substantial work to a periodic `idleTimerSourceDispatch` callback. Its stack
enters KDE's Kicker `RootModel::refresh()` and
`AppsModel::refreshInternal()`, rebuilding app/favorites model data and
notifying a QML grid view. This is a KDE runtime path, not a Latte-owned call
site; the Release executable also has no `.debug_info`, so project-side source
attribution is limited. The profile is a hotspot lead, not evidence that a
planned Latte change will reduce it.

The first planned implementation candidate remains P1a: characterize the
title-only window event route and count its hint scheduling/execution work
before changing it. This keeps the next change inside Latte's ownership and
protects the existing geometry/focus fallbacks. P0 remains pending until the
planned hidden, hover, edge-change and multi-window scenario evidence and the
M5b blocker desktop checks are recorded; do not claim an optimization or
resource reduction from the idle baseline alone.
