# P4–P6: conditional performance candidates

Status: Deferred after the conditional evaluations. The supplied Fedora
workload confirms same-view tracker duplication and an active background-shadow
consumer, but the available evidence does not establish a Release resource
benefit for changing either path. No production code was changed.

Evaluation started on branch `codex/modernization-m0-baseline` at
`521b6af76be9017dc02eb74959fe3c073a6caea1` with a clean working tree. The
current working tree contains only this report, the plan ledger and the P5
path correction in the implementation guide; the Fedora user-mode Debug Dock
is running again as PID 18994 after profiling.

## Evidence available

The P0 Fedora Release characterization records process-family CPU, context
switches and memory for idle, hidden-idle, multi-window and hover scenarios.
The five independent hover starts and live edge sequence are documented in
[P0](P0.md), with raw samples in
[P0-hover-aa-current-release-2026-10-01.jsonl](P0-hover-aa-current-release-2026-10-01.jsonl)
and [P0-edge-transitions-2026-10-01.jsonl](P0-edge-transitions-2026-10-01.jsonl).
These data establish repeatable scenarios but no before/after saving. The edge
screenshots establish the selected setting and settled visible geometry, not
layout-pass counts or frame-time tails.

## Candidate decisions

- **P4, shared per-view task query:** the user supplied a saved view containing
  app menu, app dashboard, Kicker, Trash and CPU monitor applets. A Debug QML
  trace records two `TaskManager.TasksModel` creations at the
  `AppletItem.qml:1579` tracker call site in this same containment. This proves
  same-view duplication in the selected workload, but not that a shared owner
  saves Release CPU/memory or preserves lifecycle/filter behavior. Defer the
  shared-owner refactor: model object counts alone do not establish meaningful
  savings, while sharing adds per-view ownership, app-ID subscriptions and
  teardown behavior that need their own production tests. Reopen only with
  paired Release query/work and CPU/PSS evidence that can support a bounded
  prototype.
- **P5, background shadow:** the user confirmed the shadow is visible through
  Edit Dock → Appearance → Background → Shadow. The actual path is
  `MultiLayered.qml` → `CustomBackground.qml` →
  `KirigamiShadowedRectangle.qml`; the Debug trace recorded four
  `Kirigami.ShadowedRectangle` creations at the custom-background call site.
  This corrects the earlier evaluation, which examined `ExternalShadow.qml`, a
  different shell effect path. The trace establishes active objects, not
  allocations, GPU memory, offscreen passes or frame-time cost. Keep P5
  deferred: no supported effect-on/off Release allocation, GPU-memory or
  frame-time evidence is available to identify a removable cost. Reopen only
  when such instrumentation can quantify the selected background-shadow path
  while preserving its visible output.
- **P6, pure-QML module build-time caching:** P0 runtime characterization does
  not measure QML compile/import time or rebuild scope. Defer until a clean and
  incremental build profile identifies a module with material repeated cost;
  any future change must preserve import and installation contracts.

Do not infer optimization opportunity from total process memory or CPU alone.
Reopen each candidate independently when its required metric is available, and
select a narrow change with a correctness-preserving acceptance threshold.

### P4 — per-applet task queries

Static inspection of `containment/package/contents/ui/applet/AppletItem.qml`
shows that a full `TaskManager.TasksModel`, `VirtualDesktopInfo` and
`ActivityInfo` are created only when the applet resolves at least one tracked
application ID and the task indexer is unavailable. Each such model is
screen-, desktop- and activity-filtered for its containing view; applet IDs are
filtered in the subscriber after querying. The trace observed six TasksModel
instances: two at each of `plasmoid/.../main.qml:683`,
`containment/.../Tasks.qml:16` and `AppletItem.qml:1579`. It observed three
VirtualDesktopInfo and three ActivityInfo instances, one at each of those
three call sites. The user-selected saved layout confirms the two
`AppletItem.qml:1579` tracker instances occur in one containment containing
the listed applets. This establishes same-view duplication, but the trace is
Debug-only and does not quantify Release savings. A prototype must keep the
distinct grouping/launcher model at the main task manager separate, preserve
screen/desktop/activity filters and per-applet app-ID filtering, and measure
query counts, PSS/CPU and task-state parity before acceptance.

### P5 — shadow layer/effect

The previously inspected `ExternalShadow.qml` is a separate shell effect and
is not the user's background-shadow feature. The active user-selected path is
`containment/package/contents/ui/background/MultiLayered.qml`, which configures
`colorizer/CustomBackground.qml`; its conditional Loader creates
`KirigamiShadowedRectangle.qml` when the Kirigami type is available and
`main.shadowSize > 0`. The trace observed four such rectangles in the active
setup. No effect-on/off allocation, GPU-memory or frame-time comparison has
been collected, so no P5 optimization is justified yet.

### P6 — pure-QML build-time caching

`declarativeimports/components` is currently installed as a directory of loose
QML files and `qmldir`, not as a `QML_FILES` module target. The selected local
build's `.rcc/qmlcache` contained no cached QML source files. The Debug trace
recorded compilation activity, including 3 `ToolTip.qml` events totalling
9.62 ms; seven events with basename `main.qml` totalled 884.50 ms. Basename-only
grouping is ambiguous and is not a module-specific measure.
The module exports 23 public QML types and is imported by task views,
containment, indicators, dock configuration and settings. Both configured QML
installation roots currently receive loose files plus the hand-maintained
`qmldir`; converting that whole surface to `QML_FILES` would change module
packaging and could affect local user overrides. Fedora's installed
`/usr/lib64/qt6/bin/qmltime` produced no usage text: outside Plasma,
`--help` and `-h` each aborted with exit status 134; with the active Wayland
environment, `--help` exited 255 without output. No module-specific cold/warm
Release evidence or stable alternate measurement is available. Keep P6
Deferred: the aggregate Debug trace is
ambiguous and does not justify changing this widely imported module's build,
install and override behavior. Reopen only if supported tooling can attribute
material Release compile/import time to one narrower module and a staged
build/install prototype preserves both QML roots and override precedence.

### Debian 13 Qt profiling-tool check — 2026-10-01

Debian 13 / Qt 6.8.2 also installs `/usr/lib/qt6/bin/qmltime` and
`qmlprofiler` from `qt6-declarative-dev-tools`. `qmlprofiler --help` exits 0
and documents trace capture; a QML-debug-enabled application is still
required. `qmltime` has no `--help` option: it treats that argument as a QML
file path, so the probe exits 255 with a missing-file message. Running a
minimal QML file without its required benchmark element reports
`A QmlTime.Timer instance is required.`

The following disposable harness validates the tool syntax on Debian:

```qml
import QtQuick
import QmlTime 1.0 as QmlTime
Item {
    property string name: "probe"
    QmlTime.Timer {
        component: Rectangle {
            width: 40
            height: 20
            Text { anchors.centerIn: parent; text: name }
        }
    }
}
```

`/usr/lib/qt6/bin/qmltime -iterations 20 /tmp/qmltime-probe.qml` exits 0
under the imported Plasma session and reports `Total: 0 ms, Per iteration: 0
ms`, below useful resolution for this minimal component. Qt's qmltime source
documents that it pre-instantiates the component and times repeated creation
after compilation; it is therefore useful for delegate-creation costs, not
P6's cold/warm module compilation or import cost. This closes the missing-tool
discovery gap but supplies no P6 performance evidence. Reopening P6 still
requires a cold/warm Release profile attributable to a narrow module and a
prototype that preserves both installation roots and user override precedence.

After the P5 capture, the Fedora user-mode Debug Dock was relaunched with the
Plasma session environment and development overrides; its log showed startup,
an OpenGL scene graph and no Warning/Error/Fatal/ASSERT entries. The later
`qmltime` help probes aborted without touching the running Dock. No code, saved
layout or configuration change was made for these evaluations.
