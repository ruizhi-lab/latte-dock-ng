# R5: Explain the Fedora VM idle CPU

Status: Complete. The 20 % of one core that P0 measured at idle in the Fedora VM
was produced by how the dock was launched, not by the dock. A launch from SSH
that sources `dev-env.sh` gives the dock a shorter `XDG_CONFIG_DIRS` than the
Plasma session has; the dock and the session processes then keep rewriting the
shared KSycoca database against each other, and every rewrite makes the hosted
`org.kde.plasma.kickerdash` applet rebuild its models. Reproduced on the same
binary, VM and layout (18.8 % against P0's 20.3 %), removed by one variable.
Launched with the session environment, the dock idles at 0.000–0.02 % in every
variant. No dock patch is justified; nothing under `app/`, `containment/`,
`plasmoid/` or `shell/` changed.

Date: 2026-10-27 and 2026-10-28. Branch: `claude/sweet-chaplygin-fe4acf`, started
at `eba91a3e633835e51c34cb1dd4a1c9da2da9ea9a` (main). Implementation commits:
the commit that adds this report with its data and tools, and a second commit
for the launcher documentation (see Documentation changes).

## Result

1. **The idle dock costs nothing.** The user-mode Release build of main uses
   0.000–0.017 % of one core in 13 independent idle windows of the P0 protocol
   (visible, pointer at the screen centre), wakes its main thread once per 10 s
   and draws no frame: the render thread, the llvmpipe workers and KWin run zero
   timeslices, the Wayland log has zero commits and Qt's scene-graph log zero
   frames from 5 s after the start to the end of the window. The same holds with
   the dock hidden (AutoHide, five starts), with the VM's own DodgeActive layout,
   with `QT_QUICK_BACKEND=software`, and for Plasma's panel alone (plasmashell
   0.04 %, kwin_wayland 0.01 %).
2. **P0's 20 % does not come from the dock code.** P0's exact baseline
   (v1.2.51, `e3ef1ddf0`) built and run today idles at 0.55 %, the last P0-era
   build (`96db9adcf`) at 0.68 % and the parent of R1a (`cb94d71c6`) at 0.52 %,
   each with exactly the 16 main-thread and 8 D-Bus-thread wakeups per second that
   R1a removed. R1a is re-measured in the VM: 0.52–0.55 % before, 0.000 % after.
3. **The cause is the launch environment.** Launched like P0 launched (a bare SSH
   environment, six session variables imported, `dev-env.sh` sourced), the same
   main binary uses 17.4–19.0 % of a core (five windows), 117–128 main-thread
   wakeups per second and keeps kwin_wayland at 26 % and plasmashell at 22 %; the
   VM's 1-minute load average climbs to 0.5–1.3 within a window (an idle guest
   shows 0.0–0.2, P0's records 0.6–1.9). The sycoca file is rewritten at least
   2.7 times per second. Changing only `XDG_CONFIG_DIRS` of
   the session launcher to the SSH value gives 18.7 %; the session value gives
   0.00 %; importing the session's KSycoca variables into the P0 launcher gives
   0.00 %.
4. **Who pays under that churn:** the hosted app dashboard. With the same
   change storm, the dock's cost is 11.4 % with the full layout, 10.1 % with only
   `org.kde.plasma.kickerdash`, 2.2 % without it and 1.2 % with no applets; one
   change event costs the dock about 60 ms and 60 main-thread wakeups. P0's own
   profile (Kicker `RootModel::refresh()` under a timer) and the stack samples
   here show the same owner. plasmashell and kwin_wayland react to the same storm
   with a larger share than the dock.

## Scope

Measurement and diagnosis only. The user-mode install in the Fedora VM was
replaced several times (see Files); the VM runs the plain main build again
at the end. The Debian VM and the dock on the host were not touched. No
privilege escalation was used anywhere.

## Method

- **Protocol.** P0's: independent starts, 30 s warmup, one 60 s window per start,
  `scripts/measure-process-family.py` with the dock, `latte-dock-ng-preview` and
  the add-launcher as the family. The runner [r5-scenario.py](R5-tools/r5-scenario.py)
  stops any dock, starts a fresh one, runs that collector and the per-thread
  sampler [r5-thread-sampler.py](R5-tools/r5-thread-sampler.py) over the same
  seconds, and records the KWin probe (pointer, window classes and geometry, no
  titles). Raw collector lines are kept unchanged beside this report.
- **No debug tracing.** Measurement runs have no `--debug`, except the one scenario
  that tests it. Runs with Wayland, Qt scene-graph or qmlprofiler instrumentation
  are separate and their CPU is not compared with the plain ones.
- **Launchers.** `systemd-run --user` (the Plasma session environment) unless a
  scenario says `p0-ssh`: the pattern of `docs/development-testing-guide.md`
  started from an environment equal to what an SSH command receives in the VM
  (captured with `ssh vm env`: `LANG=zh_CN.UTF-8`, no `XDG_CONFIG_DIRS`, no
  `XDG_CURRENT_DESKTOP`), six session variables imported, then `dev-env.sh`.
- **Layout.** Visible runs use `visibility=0` (AlwaysVisible, as in P0) through a
  temporary edit that the runner reverts byte for byte; every restore is checked
  by SHA-256 in the batch logs. Hidden runs use `visibility=1`.
- **Hidden and visible states** were checked on a 1920x120 strip of the bottom
  screen rows (cropped on the VM, nothing above the dock area was kept):
  `R5-data/strips/R5-main-eba91a3e6-idle-visible-quiet-start1-strip.png` shows the dock,
  `R5-main-hidden-autohide-start1-strip.png` and
  `R5-main-dodgeactive-vm-layout-start1-strip.png` (same directory) show none. The VM's own
  DodgeActive layout hides the dock whenever the active Konsole reaches the dock
  area (the Konsole window sits at the bottom of the screen after a hidden run).
- **Host load and steal.** The parent session reported heavy builds on the host.
  [host-monitor.py](R5-tools/host-monitor.py) recorded the host load average, the
  host CPU and steal and the CPU of the guest's QEMU process every 5 s for the
  whole work; each window is joined to it by time (`R5-host-monitor-windows.jsonl`
  keeps the samples around the recorded windows). The collectors also record the
  guest's steal. A window counts as taken on a busy host when the mean host CPU
  during it reached 50 %: 8 of the 89 windows (four of the first main series, one
  `96db9adcf` window, two pre-R1a ksmserver-stall windows and one pre-R1a storm
  window); they are flagged in the tables and no conclusion depends on them. Steal
  in the guest was at or below 0.61 % in every window except that storm window
  (4.4 %).
- **Per-thread data** use `/proc/<pid>/task/<tid>/schedstat` (nanosecond run time
  and the number of times a thread was put on a CPU) so that wakeups per thread are
  counted instead of inferred from 10 ms ticks. P0's collector reads
  `/proc/<pid>/status`, which counts only the main thread's context switches;
  that is what "context switches" means in every table here and in P0.

## Findings

### 1. The idle dock, P0 protocol

Session launcher, `visibility=0`, pointer at the screen centre, 30 s warmup, one
60 s window per independent start. "Main-thread ctx/s" is P0's collector figure;
"all-thread timeslices/s" counts every time any dock thread was put on a CPU.

| v1.2.51 (`e3ef1ddf0`, P0's baseline) | 3 / 0 | 0.550 (0.533–0.700) | 16.0 | 24.0 | 0.0 | 222.1 |
| `96db9adcf` (P0's last build) | 3 / 1 | 0.683 (0.666–0.766) | 16.0 (16.0–16.2) | 24.0 | 0.0 | 222.2 |

| `db966ccd6` (R1a) | 3 / 0 | 0.000 | 0.1 | 0.1 | 0.0 | 222.4 |
| `eba91a3e6` (main), three series | 13 / 4 | 0.000 (0.000–0.017) | 0.1 | 0.1 | 0.0 | 221.6 (219.8–222.9) |

The 0.017 % values are one 10 ms tick; the nanosecond figure of those windows is
0.001 %, one timeslice per 10 s. In the pre-R1a rows the 24 timeslices per second
are 16 on the main thread (0.5–0.65 % of a core) and 8 on the QDBusConnection thread
(0.04 %), the two blocking D-Bus calls of the 500 ms session poller that R1a
removed; nothing else runs. The R1a effect is therefore confirmed in the VM:
0.52–0.55 % before, 0.000 % after, 24 wakeups per second before, 0.1 after.
Four of the 13 main windows were taken while the host was busy (the parent
session's builds); they equal the nine quiet ones, as expected for a process
that has nothing to do. The initial probe of the parent's Debug build (`fc8b803d0`,
`--debug`, the VM's DodgeActive layout, pointer left at the dock; 60 s,
`R5-initial-debug-probe-*.jsonl`) read 0.017 % and 2 context switches per second.

### 2. P0's number does not reproduce with P0's own binary

P0's recorded baseline built today and run with the session launcher idles at
0.55 %, not at 20 %, and every build up to and including R1a's parent shows the
same 16 + 8 wakeups per second. The code is therefore not the variable. The
present guest is not the system P0 sampled: its `dnf history` shows no
transaction on 2026-09-30 (P0 reports an 80-package update that day; the history
jumps from 2026-09-15 to 2026-10-12), its journal has no boot on that day, Frameworks
are 6.31 where P0 recorded 6.30, and `kscreen-doctor`, which P0 found missing, is
installed. P0's raw records do carry one more fact: the guest's 1-minute load
average was 0.6–1.9 in every window, including the hidden-dock and independent-start
ones, while the dock's own 0.2 core cannot make that; today's idle guest has 0.00.

### 3. The launch environment reproduces it

P0 launched the dock from SSH with the pattern of the testing guide: six session
variables imported, then `dev-env.sh` (its Debug install says so; the Release
numbers equal what that launch gives today). The bare SSH environment of the VM
has `LANG=zh_CN.UTF-8` and no `XDG_CONFIG_DIRS`, `XDG_CURRENT_DESKTOP` or
`XDG_MENU_PREFIX`; `dev-env.sh` turns the missing `XDG_CONFIG_DIRS` into
`~/.config/kdedefaults:/etc/xdg`, while the session's value is
`~/.config/kdedefaults:/etc/xdg:/usr/share/kde-settings/kde-profile/default/xdg`.

- 18.8 % is within 8 % of P0's 20.3 %. The guest's 1-minute load average ended
  the windows at 0.5–1.3 (idle: 0.0–0.2; P0: 0.6–1.9), and the guest's QEMU process
  used 74–78 % of one host core (non-watch windows; 2.5–8 % when the guest idles).
- One variable decides it. `XDG_CONFIG_DIRS` with the session's third entry gives
  0.00 %, without it 18.7 %. The directory it names, from Fedora's `kde-settings`,
  holds default `kdeglobals`, `kde-mimeapps.list`, `kicker-extra-favoritesrc` and
  other files; why KSycoca then treats the database as stale for the other side was
  not analysed.
- The `ksycoca6_en_*` file under `~/.cache` changed 159 and 160 times in 60 s (its
  mtime sampled every 50 ms, so at least 2.7 rewrites per second) in the P0-launch
  windows and not once in the session-launcher window; no `kbuildsycoca6` process
  was started (`R5-main-p0ssh-dev-env-watch-sycoca.jsonl`), so the rewrites are
  in-process rebuilds in KSycoca clients. With the language set to `zh` the dock
  uses its own database file and nobody contests it: 0.00 %.
- P0's wakeup figure (392/s) is higher than the 126/s reproduced here, and its
  CPU per wakeup lower; the rate of the loop depends on both sides, which here are
  Frameworks 6.31 and a 4-vCPU guest.

### 4. What the dock does under that churn

studied apart from the launch:

| Full layout (tasks, global menu, trash, app dashboard) | 2 | 11.46 (11.38–11.55) | 9.61 | 108.5 | 32.2 | 17.3 |
| Without `org.kde.plasma.kickerdash` | 2 | 2.25 (2.23–2.27) | 1.34 | 15.0 | 27.8 | 17.2 |

- The hosted app dashboard is 80–88 % of the dock's storm cost; the dock's own
  reaction with no applet is 1.2 %. R1a does not change the storm cost (11.0 %
  for the one quiet pre-R1a window, 11.4–11.5 % on main); the 21.0 % window had
  4.4 % guest steal and a busy host.
- One change event costs the dock about 0.06 CPU-seconds and 60 main-thread
  wakeups (three windows each with one `kbuildsycoca6 --noincremental`, started
  3 s into a 30 s window: dock 0.200 %, 0.202 % and 0.200 %, 2.0–2.2 ctx/s;
  kwin_wayland 0.18–0.21 CPU-seconds, plasmashell 0.115). With that cost per event
  the storm's 11.4 % suggests about two events per second reaching the dock.
- plasmashell and kwin_wayland pay as much or more: they are KSycoca clients too.
  The cost is a system-wide effect of the churn, not a property of the dock.
- Stack samples of the main thread under the storm (gdb attach per sample, 150
  samples of which 12 fell into the busy part;
  `R5-main-sycoca-storm-stacks-second-pass.txt`): `QTimer::timeout` below
  `QTimerInfoList::activateTimers` below `idleTimerSourceDispatch` in 8 of the 12,
  `RootModel::refresh` in 5, `AppsModel::refresh` and
  `AppsModel::refreshInternal` in 4, `QAbstractItemModel::dataChanged` in 7, a
  `QQuickGridView` delegate re-creation in 3 and an ICU collator comparison (sorting
  application names) in 1. That is the stack that P0 recorded with `perf record -g`
  ("a periodic `idleTimerSourceDispatch` callback entering Kicker
  `RootModel::refresh()` and `AppsModel::refreshInternal()`"), now with its trigger
  named. A second storm run with `eu-stack` (400 samples, 43 busy,
  `R5-main-sycoca-storm-eustack.txt`) has the same `idleTimerSourceDispatch` in 17,
  `QAbstractItemModel::dataChanged` in 21 and `KApplicationTrader::query` /
  `KServiceFactory::createEntry` in 13, plus `TaskManager::WaylandTasksModel::data`
  (`windowUrlFromMetadata`) in 14; the stacks cannot say whether that model belongs
  to the dashboard or to the tasks plasmoid, so the layout table above, not the
  stacks, apportions the cost. The first pass (90 samples, 4 busy, `R5-main-sycoca-storm-stacks-first-pass.txt`)
  found `SimpleFavoritesModel::refresh`, `KFilePlacesModel` and
  `Solid::Device::listFromQuery`; a single `eu-stack` probe of the P0-launched dock
  caught `KFilePlacesModelPrivate::reloadBookmarks()`. All of it is code of the app
  dashboard's models, not of the dock.
- Stack samples of the P0-launched dock (`eu-stack`, 400 samples about 0.2 s apart,
  66 of them in the busy part; `R5-main-p0ssh-eustack.txt`): `KSycoca::ensureCacheValid`
  below `KSycocaPrivate::checkDatabase`, `KSycocaPrivate::buildSycoca` and
  `KBuildSycoca::recreate` (then `build` and `createEntry`) in 35 of the 66, below
  `KAStatsFavoritesModel` (the app dashboard's favorites model: `initForClient`,
  `Private::addResult`, `entryForResource`, `AppEntry::AppEntry`,
  `KService::serviceByStorageId`) in 43, and the dashboard's `QQuickGridView`
  regeneration (`regenerate`, `addVisibleItems`, `createItem`) in 12–14. So the dock
  itself rebuilds the sycoca database in its main thread whenever the dashboard's
  models resolve a service, because its `ensureCacheValid()` finds the file stale for
  its own environment, and plasmashell and kwin_wayland do the same from the other
  side. gdb attached for every sample, which freezes the dock for about 2 s, and the
  loop did not survive it: 150 of 150 gdb samples sat in `ppoll`
  (`R5-main-p0ssh-stacks.txt`, kept as a negative result).

### 6. Frames, renderer and scene graph

- **Backend and renderer.** From the dock's own log of an instrumented Release run
  (`R5-data/logs/r5-dock-main-frames-idle.log.gz`): `threaded render loop`,
  `Animation Driver: using vsync: 16.67 ms`, `Creating QRhi with backend OpenGL`,
  `OpenGL VENDOR: Mesa RENDERER: llvmpipe (LLVM 22.1.8, 256 bits) VERSION: 4.6
  (Compatibility Profile) Mesa 26.2.5`. `eglinfo -B` (GBM and Wayland platforms)
  reports `llvmpipe (LLVM 22.1.8, 256 bits)`, `glxinfo -B` says `Accelerated: no`,
  KWin composes with `gl2` on EGL on the same llvmpipe (kwin_wayland has four
  `llvmpipe-N` worker threads) and the guest's virtio-vga has no 3D, so virgl is not
  in use. The dock's line `Latte Dock actual Qt Quick scene graph graphics API:
  OpenGL (GPU accelerated: true)` is therefore misleading in this VM: `true` is
  derived from the API type alone in `app/view/view.cpp`, not from the renderer
  (an observation; it is not changed here).
- **Idle frames, three counters, all zero.** Over the idle window of an instrumented
  Release start (`QSG_RENDER_TIMING=1`, `qt.scenegraph.time.renderloop=true`,
  `WAYLAND_DEBUG=client`, `--debug --log-file`): Qt's scene-graph log has 22
  `syncAndRender` frames, all within 5.4 s of the start and none afterwards; the
  Wayland log has 24 commits in the whole 91 s (22 in seconds 1–5 of the start, 20 of
  them with a new buffer, and two at shutdown without one) and none in between,
  so none in the window (seconds 32–90); the sampler counts
  zero timeslices of `QSGRenderThread` and of every `llvmpipe` worker of the dock,
  and of kwin_wayland and its workers, in every idle window of this report.
  KWin's `supportInformation` reports the 60 Hz refresh rate and the renderer but no
  frame counters; its other frame statistics are in the GUI debug console and the
  FPS effect, which repaints continuously and would end the idle state, so its
  worker timeslices are the proxy. The session bus carried 0 messages in 30 s with the dock
  running and 8 (0.27 per second) with it stopped (`R5-dbus-session-idle-*.json`).
- **What a frame costs here.** The attention animation draws 60 frames per second
  (the Wayland log has a maximum of 60 commits in a second, 300 commits with a new
  buffer on the view's surface in about 5 s, each damaging the whole surface). In
  the two plain 20 s windows the dock used 2.6 CPU-seconds, 7.0 ms of every frame in
  the llvmpipe workers and 8.7 ms in total: 52 % of a core for a 60 fps animation.
  P0's 20 % would be about 23 such frames per second, but the dock drew almost
  none in the P0-launch windows: the llvmpipe workers used 1.0 % of the 18.8 %, the
  main thread 17.3 %. The loop's cost is model work in the main thread, not rendering,
  and software rendering would not have removed it (it saves 90 MiB of PSS, not CPU).

## Limits

- P0's exact rate (392 wakeups per second, 20.3 %) was not reproduced, only its
  class: 118–128 wakeups per second and 17.4–19.0 % on the same launch. Frameworks
  6.31 here against 6.30 there, the guest's resources and window set may differ.
- Why KSycoca treats a database built under the shorter `XDG_CONFIG_DIRS` as stale
  for the session processes, and the other way round, is inside KDE's kservice and
  was not analysed. The bisect proves the variable, not the field inside the
  database.
- The loop needs two sides with different environments; the dock is one of them
  and plasmashell and kwin_wayland pay more than the dock does. A dock started
  by Plasma's autostart or by `systemd-run --user` has the session environment and
  does not take part (0.000–0.02 % in every idle window launched that way).
  Launches from other contexts with a different `XDG_CONFIG_DIRS` (cron, a service,
  `env -i`) were not tested; only an SSH-equivalent environment was.
- One guest (4 vCPUs, one 1920x1080 output, llvmpipe, Frameworks 6.31, GCC only).
  The Debian VM, hardware and a second output were not measured; no clang build
  was possible in this VM.
- The stack samples are statistical (12 busy samples of 150 in the storm); they
  identify the owning code, they do not apportion time exactly.
- The artificial storm is a model of the churn, not a record of what P0's guest had.
